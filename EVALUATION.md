# Evaluation plan

Written on 2026-11-17, before the held-out platform was audited. It does not change after the `frozen-test` tag.

## Question

Does a read-only audit with these checks find the defects that matter in a Python clinical ML repository (data leakage, model execution integrity, failure handling, reproducibility, dependencies, tests, integration), and does it stay quiet on a repository without them?

## Test material

| Platform | Role | Task | Who wrote it | Defect list |
|---|---|---|---|---|
| `platform_a` (WardWatch) | development | ward deterioration within 48 h | written alongside the checks | 15 planted, in `stand_in/manifests/platform_a_defects.json` |
| `platform_a_clean` | development control | same code without the defects | same | none |
| `platform_b` | held-out test | written separately, different code base and task | written separately from the checks, with a sealed defect list | sealed until after the frozen run |
| `platform_b_clean` | held-out control | same code without the defects | same | none |

All data are synthetic and generated by each platform's own seeded generator. No real patient data are used.

## Rules for the held-out run

1. The checks were developed on platform A only. Platform B's audit settings (`targets/platform_b*.yaml` and its adapter) are written from platform B's README alone, without reading its code.
2. The toolkit, targets and this plan are committed and tagged `frozen-test` before platform B is audited.
3. Platform B and its clean twin are audited once each, with 40 mutants per platform and fixed seeds.
4. Only then is the sealed defect list opened and the run scored with `mlaudit/score.py`.
5. Any change to the checks after the frozen run is a post-hoc fix. It goes in a separate commit and is reported as a second result beside the frozen one.

## Scoring

- **Located match.** A finding counts as detecting a planted defect when it names the same file, cites a line within three lines of the defect's range, and has the same category.
- **Unlocated dynamic match.** Some checks run the platform and report a behaviour rather than a line, such as patients in both train and test, or served scores that differ from validated ones. These findings can match a defect of the same category only if that defect has no located match.
- **One-to-one.** Each finding matches at most one defect, and each defect at most one finding (maximum bipartite matching).
- **Unlocated matches are checked by hand.** Each one is confirmed by reading the finding's evidence against the defect description, and the hand-checked count is reported beside the automatic count.
- **Baseline.** ruff (default rules) and bandit (assert rule off), plus the platform's own test suite, counted with the same file and line window and with category ignored, which favours the baseline.
- **False alarms.** These are counted on the clean twins. The headline is the number of Critical or High findings, with Medium and Low counts listed.

## Reported numbers

The report gives: defects detected out of those planted (automatic, then hand-checked); Critical and High defects detected; baseline detections; and clean-twin findings by severity. Each comes with the exact denominators. With 15 or so defects per platform, a proportion has a wide interval: a Wilson 95% interval is reported for the held-out detection rate.

## Limits stated in advance

- The planted defects are a sample of known defect types. They are not a random sample of real-world defects.
- The person who wrote the checks also chose the defect categories. The held-out platform's code and its specific defects were written separately and kept sealed, but this is not a fully blind test.
- Passing these checks does not make a model clinically valid. Clinical evaluation is a separate step.
